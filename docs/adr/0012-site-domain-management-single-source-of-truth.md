# ADR-0012: Site & Domain Management (Single Source of Truth)

**Status:** accepted

**Date:** 2026-08-17

## Context

Phase 4 maps local domains (e.g. `acme.test`) to project directories served over HTTPS. Three artifacts must stay in agreement for a domain to work end-to-end:

1. **Hosts file** — resolves `acme.test` to `127.0.0.1` (needs elevation on Windows).
2. **Caddy config** — routes `acme.test` to the project's dev server port and terminates TLS.
3. **TLS certificate** — the cert's SANs must include every served domain.

If each service edits its own artifact independently, the three drift apart and the feature silently breaks (a domain resolves but returns a cert error, or a deleted project keeps a hosts entry pointing nowhere).

## Decision

Introduce a `SiteManager` that is the **single owner of the domain→project mapping**; hosts, Caddy routes, and certs are _derived_ outputs it pushes to, never edited by other services.

- **Data model:** the `projects` table carries `domains` (JSON array) and `ssl_enabled` (ADR-0006's reserved Phase 4 fields, added via migration [ADR-0010](0010-sqlite-migration-mechanism.md)). A "site" is just a project with one or more domains.
- **Hosts:** `HostsFile` helper performs read-modify-write with a backup + write-time change detection, only ever removes lines tagged `# Horde managed`, respects pre-existing user entries (no duplicate), and reports (rather than overwrites) user entries that map a domain elsewhere. Writes go through the elevation abstraction ([ADR-0011](0011-privileged-operation-elevation.md)).
- **HTTPS:** a single **wildcard certificate `*.test`** generated by mkcert (CAROOT pinned to the app-managed cert store). Because the wildcard covers all current and future `.test` domains, adding/removing a project domain never requires cert regeneration — this eliminates the largest sync failure point. `mkcert -install` and the trust-store install are idempotent and elevation-aware.
- **Proxy:** `SiteManager.apply()` recomputes the route table and hands it to [Caddy](0013-caddy-reverse-proxy-as-managed-service.md) via `setRoutes()`, which regenerates and reloads the Caddyfile.
- **Project removal** flows through `SiteManager.removeProject()`, which deletes managed hosts entries and re-applies routes — no stale domains survive deletion.
- **No cross-feature coupling in the renderer:** a `sites` FSD feature module exposes the IPC surface; the Sites page composes it with the projects store.

## Consequences

**Easier:**

- One place to reason about domain correctness; sync is deterministic per domain change.
- Wildcard cert keeps HTTPS universally working for new sites with zero cert churn.
- Cleanup is centralized: removing a project provably removes its hosts entries and routes.

**Harder:**

- Hosts editing requires a UAC prompt per write on Windows (accepted per ADR-0011); denied elevation surfaces a clear error and leaves the app functional.
- The fallback proxy target is a fixed port when a project's dev server is not running, so Caddy returns 502 until the server starts (the Sites UI documents "start the dev server first").
- Managed/untagged hosts entries coexist; a domain a user maps manually is respected but will not be cleaned up by Horde.

**Follow-up:**

- `SiteManager` + `HostsFile` (done, Phase 4).
- `MkcertManager` wildcard cert (done, Phase 4).
- `sites:*` IPC + Sites page (done, Phase 4).

## Alternatives Considered

- **Per-project certificates.**
  - **Rejected because:** Every domain add/remove requires regenerating a cert and keeping its SANs in sync with two other stores — exactly the drift this ADR exists to avoid. A wildcard over the reserved `.test` TLD is safe (no public CA will ever issue `.test`).
- **Let each service manage its own artifact.**
  - **Rejected because:** No single component can guarantee consistency; removal cleanup and conflict handling would be duplicated or forgotten.
